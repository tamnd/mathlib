**Cadence.** There is one minor version per month: 12 stable minors (v4.25 to v4.36) in the 12 months from Nov 2025 to Nov 2026. The pattern is:

- `vX.0-rc1` ships within about 0 to 3 days of the previous stable.
- Zero to three more RCs follow (v4.29 needed eight).
- Stable ships about 4 to 6 weeks after rc1.
- Patch releases (`.1`, `.2`) come out occasionally, between minors.

The community "tags and branches" page says: "Stable releases usually arrive near the middle of the month" and "The first release candidate of the next version is released immediately after the stable release" (https://leanprover-community.github.io/contribute/tags_and_branches.html). There are a few outliers. v4.29 to v4.30 took about two months (Mar 27 to May 26). v4.36's stable came out 2026-11-16.

Lean release notes live in the reference manual, e.g. https://lean-lang.org/doc/reference/latest/releases/v4.36.0/ and https://lean-lang.org/doc/reference/latest/releases/v4.37.0/. The GitHub release bodies just link there.

Nightlies: the `nightly` branch is in `leanprover/lean4`, and dated tags `nightly-YYYY-MM-DD` are in `leanprover/lean4-nightly` (https://github.com/leanprover/lean4/blob/master/.claude/commands/release.md, "Nightly Infrastructure" section).

### 1.3 How a Mathlib tag is cut

Lean's release tooling (`script/release/checklist.py`, `script/release/repos.py`) drives the release across the whole ecosystem (https://github.com/leanprover/lean4/blob/master/doc/dev/release.md). The comment on the `MATHLIB4` entry in `repos.py` (https://github.com/leanprover/lean4/blob/master/script/release/repos.py) says:

> To create a new release, open a PR into `master`. In it, bump the toolchain and all dependencies. For `v4.X.0-rc1` releases, use the existing `bump/v4.X.0` branch. After merging the PR, create a new `bump/v4.X+1.0` branch off of `master`. For other releases, create a new branch off of `master` and use it for the PR. Once the release PR is merged, tag the resulting commit with the lean version. Then, update the `stable` branch to point to the same commit.

`repos.py` also sets `patch_release=True`, because Mathlib needs a tagged release for every Lean patch release so that the olean cache exists for that toolchain. It lists Mathlib's "strong deps" as batteries, Qq, aesop, ProofWidgets4, import-graph and plausible. These are tagged first.

So the tag is **the master commit that moves the toolchain** to the new Lean version. It is a snapshot of master at that point, not a separately stabilised branch, and it is not backported. Master moves onto the next RC right away: on 2026-11-26 master's `lean-toolchain` is already `v4.37.0-rc1`.

### 1.4 What the branches mean

| Ref | Where | Meaning | Source |
|---|---|---|---|
| `master` | mathlib4 | Development head. Bors merges about 25 to 40 commits a day. Its toolchain is always the newest Lean **stable or RC**. A CI-built olean cache is available for every master commit. | https://leanprover-community.github.io/contribute/tags_and_branches.html |
| `vX.Y.Z[-rcN]` tags | mathlib4 | The first master commit on that toolchain. Cache available. Recommended stepping stones for downstream projects. | wiki, see 5.1 |
| `stable` | mathlib4 | Moved to each stable `vX.Y.0` tag. Currently fc4f59e577 = v4.36.0. | `repos.py`; `gh api repos/leanprover-community/mathlib4/branches/stable` |
| `bump/v4.X.0` | **now on mathlib4 itself** (`bump/v4.38.0` exists on 2026-11-26) | Prepares master to build on the next Lean. Uses nightly toolchains, is reviewed, and "should always build without errors". It is merged into master when rc1 ships. | tags_and_branches page; branch list API |
| `nightly-testing` | fork `leanprover-community/mathlib4-nightly-testing` | Historically: daily Lean-nightly adaptations, not reviewed, "not guaranteed to build". It was **retired in Nov 2026**, see below. Its last toolchain was `nightly-2026-10-30`. | https://github.com/leanprover-community/mathlib4-nightly-testing |
| `nightly-testing-YYYY-MM-DD` tags | fork | Green nightly snapshots. The last ones are from 2026-10. | fork tags API |
| `lean-pr-testing-NNNN` | fork | "Obsolete", replaced by `leanprover/downstream-lean4`. | tags_and_branches page |

**Nov 2026 change: the legacy nightly pipeline was retired.** Two PRs did this:

- mathlib4#45594 "ci: retire the legacy Lean nightly pipeline" (https://github.com/leanprover-community/mathlib4/pull/45594) stops the daily merge into `mathlib4-nightly-testing`. The daily checks "test `master` and the newest `bump/v4.*.0` branch". Bump failures link to `downstream-lean4`, "which receives the fixes".
- mathlib4-nightly-testing#316 (https://github.com/leanprover-community/mathlib4-nightly-testing/pull/316) was merged 2026-11-13.

Lean adaptations now come from **`leanprover/downstream-lean4`** (https://github.com/leanprover/downstream-lean4). It is a pseudo-monorepo of local copies of key packages, all on Lean nightly, with branches `green-nightly-YYYY-MM-DD` and `green`. Adaptations are exported as PRs into Mathlib's current bump branch, e.g. "chore: downstream-lean4 adaptations for nightly-2026-11-19 (#46257)" on `bump/v4.38.0`.

Two things are now partly out of date. The community page https://leanprover-community.github.io/contribute/tags_and_branches.html still describes `bump/*` as living on the fork. Lean's own `.claude/commands/release.md` still says "Mathlib `bump/v4.X.0` branches live on the fork". In fact, `bump/v4.38.0` was present on the main repo, while the fork's newest `bump/v*` branch is `bump/v4.29.0`. So the location appears to have moved recently (**partly unverified**: only the branch lists were checked).

## 5. Update mechanisms for downstream projects

### 5.1 Lake basics

- **Require.** Use `[[require]] name = "mathlib" scope = "leanprover-community"` (optionally `rev = "v4.X.Y"`), or in `lakefile.lean` write `require "leanprover-community" / "mathlib" @ git "v4.X.Y"`. Source: https://github.com/leanprover-community/mathlib4/wiki/Using-mathlib4-as-a-dependency
- **`lake update [mathlib]`.** This re-resolves `inputRev` to a new `rev` in `lake-manifest.json`. By default it **also updates the root `lean-toolchain`** when a dependency needs a newer toolchain (pick the newest compatible one, then restart with the new Lake). `--keep-toolchain` disables that. It never discovers new Lean releases by itself. Sources: https://lean-lang.org/doc/reference/latest/Build-Tools-and-Distribution/Lake/ and https://github.com/leanprover/lean4/issues/2752 (implemented by lean4#5684, late 2024).
- **Cache hook.** Mathlib's `lakefile.lean` has a `post_update` hook that runs `lake exe cache get` automatically in downstream projects. It is skipped when the running Lake version differs from the toolchain, or when `MATHLIB_NO_CACHE_ON_UPDATE=1` (https://github.com/leanprover-community/mathlib4/blob/master/lakefile.lean).
- **`lake exe cache get`.** Downloads pre-built `.olean`s for the exact Mathlib commit. The cache exists for every master commit and every tag. That is why Lean patch releases also get Mathlib tags (`patch_release=True` in `repos.py`).
- **Official advice.** The wiki says jumping straight to master "may be unwise, especially for large projects or ones far behind". Instead, step through the tagged releases and fix breakages at each tag. Declarations get renamed or moved, so adding `import Mathlib` helps when something seems to have vanished.
- **Mathlib's own deps** (`lake-manifest.json` on master) are all on branch heads (`main`/`master`): batteries, Qq, aesop, proofwidgets, importGraph, LeanSearchClient and plausible. `Cli` is pinned to `v4.37.0-rc1`.

### 5.4 Deprecation policy and machinery

- **Declarations.** A renamed lemma keeps `@[deprecated (since := "YYYY-MM-DD")] alias old := new`, or `@[deprecated new (since := …)] theorem …`. The warning text is "`X` has been deprecated … Use `Y` instead", which `scripts/fix_deprecations.py` parses to auto-rewrite (https://github.com/leanprover-community/mathlib4/blob/master/scripts/fix_deprecations.py). There is also a `deprecate to` command in `Mathlib/Tactic/DeprecateTo.lean`, plus `scripts/add_deprecations.sh`.
- **Retention window: about 6 months.** `.github/workflows/remove_deprecated_decls.yml` runs **on the 15th of every month** and removes declarations deprecated between "5 years ago" and **"6 months ago"** by default, using the `#clear_deprecations` command (`Mathlib/Tactic/Linter/FindDeprecations.lean`). Example: bot PR #42655 "remove declarations deprecated between 2021-08-11 and 2026-02-11" (https://github.com/leanprover-community/mathlib4/pull/42655), closed 2026-09-15.
- **Modules.** When a file is renamed or split, it is replaced by a shim containing `deprecated_module "…" (since := "…")`, which re-exports the new locations and warns on import (`Mathlib/Tactic/Linter/DeprecatedModule.lean`; docs mirror http://florisvandoorn.com/carleson/docs/Mathlib/Tactic/Linter/DeprecatedModule.html). CI labels un-annotated removals `file-removed`. Shims are bulk-deleted after about 6 months. Examples:
  - #36510 "delete >6 month old deprecated modules" (2026-03-23)
  - #37974 "delete deprecated modules up to 14 October 2025" (2026-04-13)
  - #44239 "delete deprecated modules to March 2026"

  `scripts/create_deprecated_modules.lean` generates shims. There was a known bug where `shake` stripped shim imports; it was fixed by #44077, which protects them with `-- shake: keep-all`. Sources: https://github.com/leanprover-community/mathlib4/pull/36510, https://github.com/leanprover-community/mathlib4/pull/37974, https://github.com/leanprover-community/mathlib4/pull/44239, https://github.com/leanprover-community/mathlib4/pull/44077
- **The `Mathlib/Deprecated/` folder** now holds only `Aliases.lean`: "Deprecated aliases can be dumped here if they are no longer used in Mathlib, to avoid needing their imports". It shrank from 6 files at v4.24.0 to 1. Older deprecated theories (`Deprecated.RingHom`, `Deprecated.Sort`, `Deprecated.Estimator`, `MLList.BestFirst`) were deleted by #36510 and #37974.
- **Current volume** (GitHub code search, which counts files and is approximate): about **1,172 files** under `Mathlib/` contain `deprecated (since`, and about **154 files** contain `deprecated_module` (`gh api search/code -f q='"deprecated (since" repo:leanprover-community/mathlib4 path:Mathlib'`).
- **No single official written policy page** was found. The 6-month figure comes from the workflow defaults and the PR titles above (search summary at https://github.com/leanprover-community/hopscotch: "The shim itself is bulk-deleted about six months after that").

### 5.5 Breaking-change rates (measured)

- **Module churn** (tree API diffs of `Mathlib/**/*.lean`):

  | Span | Added | Removed or renamed |
  |---|---|---|
  | v4.35.0 to v4.36.0 (1 month) | 120 | 32 |
  | v4.30.0 to v4.36.0 (about 6 months) | 767 | 149 |
  | v4.24.0 to master (about 13.5 months) | 2,075 | 334 |

  That is about **25 module paths disappear per month**. Each one leaves a 6-month `deprecated_module` shim, so imports break hard only for projects more than about 6 months behind.
- **Commits:** about 800 per month, and 835 between v4.35.0 and v4.36.0.
- **Declaration-level breakage** per FLT bump PR (about 1 to 2 weeks of Mathlib) is typically 2 to 5 distinct upstream PRs needing fixes, for example the three cited in FLT#1205 (https://github.com/ImperialCollegeLondon/FLT/pull/1205). Some changes have no alias at all, such as structure-field removals like `MulEquivClass.map_mul`, so they break immediately. I found no global "breaking changes per release" statistic (**unverified**).

## 6. Large 2025 to 2026 changes a "latest-tracking" handbook must handle

1. **The module system (`module`, `public import`, `@[expose] public section`, `meta import`).**
   - Introduced experimentally in Lean v4.22.0 (2025-08-14). In modules, `private` became the default visibility (https://lean-lang.org/doc/reference/latest/releases/v4.22.0/).
   - Mathlib switched wholesale in **#31786 "chore: move Mathlib to the module system" (2025-11-19)**, verified in the history of `Mathlib/Logic/Basic.lean`.
   - Every file now starts with `module`, then `public import …` (or `public meta import Aesop`), then the module doc, then `public section` (e.g. https://github.com/leanprover-community/mathlib4/blob/master/Mathlib/Algebra/Group/Basic.lean).
   - #41950 (merged 2026-09-28) set `requiresModuleSystem`, so non-module downstream projects now get a warning, silenced with `allowNonModules`. It says future Mathlib "might drop support" for non-module users (https://github.com/leanprover-community/mathlib4/pull/41950).
   - Since late 2026 there have been ongoing "demote public imports" passes, e.g. #43918 (2026-09-28) and #46228 "make 639 `public import`s private" (2026-11-21). **These change which declarations are transitively visible**, so downstream imports may need to become more specific.
   - Archive was converted (#42010, #42242), and so were tests and docs (#45107, #45134).
   - Lean v4.36 made module imports faster and stopped exporting proof-only equation lemmas (https://lean-lang.org/doc/reference/latest/releases/v4.36.0/).
   - **Consequence for `mathlib-lean`:** the companion package must itself be written as `module` files, and must `public import` the specific Mathlib modules it needs.
2. **The `grind` tactic.**
   - It shipped in Lean v4.22.0 as an SMT-style tactic with theory solvers and Gröbner bases (https://lean-lang.org/doc/reference/latest/releases/v4.22.0/, https://x.com/leanprover/status/1956440244825493766).
   - Usage figures: about 3,400 uses across 2,400 Mathlib theorems as of Feb 2026, half of them refactors (system-description paper, https://link.springer.com/chapter/10.1007/978-3-032-32589-1_7). "4,000+" appears in de Moura's NFM 2026 talk (https://leodemoura.github.io/static/nfm2026/). Code search on 2026-11-26 finds about 1,592 `Mathlib/` files mentioning `grind` (a file count, approximate).
   - Mathlib has `Mathlib/Tactic/GrindAttrs.lean` and lemmas tagged `@[grind]`.
   - The options keep evolving. In v4.37, `splits` was renamed to `branches` and `verbose` now defaults to false (https://lean-lang.org/doc/reference/latest/releases/v4.37.0/). Proof text in the handbook will churn as proofs get golfed into `grind`.
3. **Folder reorganisations.**
   - The **`Basic/` top folder** came in #39703 (2026-08-26). It moves "basic predicates on types and basic mathematical types" out of `Logic`/`Data`, so `Data` is meant to become "data structures" only. The PR notes that "Many more files (~1000) could be moved", and some will go to `Algebra.Order` or be deprecated (https://github.com/leanprover-community/mathlib4/pull/39703). **Expect continued large renames from `Data/*` and `Logic/*` to `Basic/*`.** So far 52 files have moved (e.g. `Basic/ENNReal`, `Basic/Real`, `Basic/Countable`, `Basic/Complex`).
   - **`Wanted/`** for `proof_wanted` (#42284, 2026-08-11).
   - `Mathlib/Std` was removed, and `Mathlib/Deprecated` shrank to `Aliases.lean`.
   - Many module splits are driven by `linter.style.longFile` (1,500-line limit, in `lakefile.lean`), e.g. today's "split `Topology/Sheaves/KSheaf` (#46489)".
4. **`Mathlib.Tactic` changes since v4.24.**
   - Removed: `CC` (congruence closure, superseded by `grind`), `ExtractLets`, `LiftLets`, `GeneralizeProofs`, `Propose`, `RewriteSearch`, `Recall`, `LinearCombination'`, `ToAdditive/Frontend` and `GuessName`.
   - New: `Translate/` (a generic translation attribute behind both `@[to_additive]` and the new `@[to_dual]`), `ClickSuggestions/`, `ComputeAsymptotics/` (multiseries), `Inclusion/`, `Echelon/`, `Hessenberg/`, `Determinant/`, `NormDet`, `NormCharpoly`, `ModuleNF`, `GrindAttrs` and `DefEqAbuse`, plus 16 new linters.
   - `irreducible_def` is being deprecated (#46365, https://github.com/leanprover-community/mathlib4/pull/46365).
5. **Verso docstrings.** #45031 / #45466 (Oct 2026) enable `doc.verso` in 1,352 files whose doc-gen output does not change (https://github.com/leanprover-community/mathlib4/pull/45031). Lean v4.36 replaced the Verso docstring parser: tabs are now banned, and the link syntax changed. **Docstring extraction for the handbook must handle both Markdown and Verso docstrings.** doc-gen4 still converts them back to Markdown.
6. **Release infrastructure moves.** The nightly-testing pipeline was retired in Nov 2026 (section 1.4), and the downstream-reports and hopscotch services are new (section 5.2). Tooling that scraped `nightly-testing` tags should switch to `bump/v4.*` and `downstream-lean4` `green*` branches.
7. **Performance and size.** Lean v4.36 claims Mathlib builds about 12% faster (release notes). A cold `lake exe cache get` remains the only practical way to get oleans. Sizes are **unverified** (several GB in `.lake`).

## 7. Implications for a project that tracks latest Mathlib

The context is four repos: `mathlib` (map/data), `mathlib-lean`, `mathlib-agent` (Go) and `mathlib-handbook`. The siblings currently pin v4.35.0 (56a005855e). That pin is already one stable behind (v4.36.0, 2026-11-16) and about 1,100 commits behind master.

### 7.1 What to pin: a two-tier strategy

1. **Data and map repo (`tamnd/mathlib`): follow `master` directly. It does not need to compile against Mathlib.**
   - Regenerate daily from the tree API plus a doc-gen or declaration dump at a recorded commit SHA.
   - Store `{mathlib_sha, lean_toolchain, generated_at}` in every artifact.
   - Also produce a snapshot at each `vX.Y.Z` tag, so handbook editions can cite stable identifiers.
2. **Lean companion (`tamnd/mathlib-lean`): track `master`, but bump through LKG, not raw HEAD.**
   - Write it as `module` files from day one, because `requiresModuleSystem` is on.
   - Register it in `downstream-reports` (PR to `ci/inventory/downstreams.json`) and copy PFR's workflow: `track-incompatibility` with `open-pr: true` on a 6-hour cron, or `bump-to-latest` plus `open-bump-pr` daily.
   - This gives the freshest commit that is known to build, along with the exact FKB commit when something breaks.
   - Fallback if you don't want to register: `leanprover-community/mathlib-update-action` with `intermediate_releases: latest`, which goes to the newest tag and then master.
3. **Handbook (`tamnd/mathlib-handbook`): publish editions keyed to stable tags.** Cut a PDF/EPUB edition per stable Mathlib tag, i.e. monthly around the 15th, plus an optional "rolling" web build from master.
   - Edition naming: "Edition 2026.11 (Mathlib v4.36.0, fc4f59e577)".
   - Never key prose to RC tags. RCs can repeat (v4.29 had 8 RCs), while stable tags are immutable and cached.
4. **Toolchain.** Read the toolchain from Mathlib's `lean-toolchain` at the chosen SHA. Never hand-maintain it, because `lake update` propagates it automatically. The local v4.36.0 toolchain matches the current stable tag. Master needs v4.37.0-rc1, which elan installs on demand.

### 7.2 Bump cadence

- Tag-stepping (stable only) means 12 bumps a year with large diffs: about 120 new modules, about 30 removed modules, and about 835 commits each.
- Master via LKG daily or 6-hourly means tiny diffs, usually 0 to 2 breakages a week (FLT and PFR experience).
- **Recommendation:**
  - `mathlib-lean`: daily LKG bump (automatic).
  - Data repo: daily regeneration.
  - Handbook: monthly edition at each stable tag.
- **Never fall more than about 5 months behind.** After about 6 months, deprecated aliases and module shims are deleted: the monthly removal workflow runs on the 15th and removes anything deprecated more than 6 months earlier. After that, renames become hard breaks with no hints.

### 7.3 How `mathlib-agent` should detect renamed or deprecated declarations

1. **Diff declaration sets between consecutive SHAs** (from `doc-gen4` JSON or a `lean4export`/environment dump). Classify each change as added, removed, or "removed but present as a `@[deprecated]` alias".
2. **Harvest the deprecation table.** Scan for `@[deprecated X (since := "…")]` and `@[deprecated (since := …)] alias old := new` to build a map from old name to new name, with the date. The authoritative form is the compiler warning "`old` has been deprecated… Use `new` instead". Mathlib's own `scripts/fix_deprecations.py` parses exactly this, so the same regex works for building the companion and rewriting handbook snippets.
3. **Harvest module shims.** Find files containing `deprecated_module` to get the map from old module to replacement imports. Alternatively, run `hopscotch dep … --scan-mode linear` and then `hopscotch fix apply` to rewrite imports automatically.
4. **Track the removal horizon.** For each alias, the expected deletion date is `since + 6 months`, rounded to the next 15th. Flag handbook references that use a deprecated name before that date.
5. **Handle silent breaks.** Some breaking changes add no alias, e.g. structure-field removals such as `MulEquivClass.map_mul`, or `public import`s demoted to private, which change transitive visibility. Here the build failure is the only signal. Rely on the downstream-reports FKB commit, read that PR's title and body, and log it in a "breaking changes" ledger, as FLT bump PRs do by hand.
6. **Watch the reorganisation PRs.** Large ongoing moves are `Data`/`Logic` to `Basic` (about 1,000 files planned) and file splits from the 1,500-line linter. Key handbook chapters by **declaration name plus a stable concept id** (e.g. the `overview.yaml` or `undergrad.yaml` key, or the Wikidata Q-id from `1000.yaml`), not by file path.
7. **Curriculum sources to re-ingest on every bump:** `docs/overview.yaml` (504 entries), `docs/undergrad.yaml` (562 entries, about 133 missing), `docs/100.yaml` (100 entries, 78 formalised), `docs/1000.yaml` (1,199 entries, 220 in Mathlib) and `Wanted/**/*.lean` (`proof_wanted`). Their declaration names are validated by Mathlib CI (`scripts/yaml_check.py`), so they are a reliable seed index. A handbook rename-check can verify every name against these files at each SHA.
